# Decision Log: HKM Program Operations Portals

Created: 2026-06-10

## Decisions Captured

1. Use one Next.js application for both Gita Life and FOLK portals.
   - Source: User discussion with architect and party-mode rounds.
   - PRD coverage: Sections 1, 4.1, 7.
   - Status: Superseded by decision 10 on 2026-06-11.

2. Support separate program experiences and subdomains.
   - Source: User asked about separate subdomains for Gita Life and FOLK.
   - PRD coverage: FR-2, section 5.

3. Public pages should link to branded Program Portals.
   - Source: User asked how an operations button should appear on FOLK and Gita Life pages.
   - PRD coverage: FR-1, FR-3.

4. Avoid public wording such as backend/admin/operations.
   - Source: Party-mode UX discussion recommended FOLK Portal and Gita Life Portal.
   - PRD coverage: FR-1, section 7.

5. Airtable Team is the operational source of truth.
   - Source: User stated Airtable should be source of truth because they purchased Team plan.
   - PRD coverage: Sections 1, 4.3, 7.

6. Supabase remains the runtime identity and authorization layer.
   - Source: Architect, engineer, product, and QA discussion.
   - PRD coverage: Section 4.2.

7. Users can belong to both Programs with different Roles.
   - Source: Discussion of two separate Airtable Bases and one Supabase Auth identity.
   - PRD coverage: FR-4, FR-6, section 7.

8. FOLK and Gita Life should have similar feature families.
   - Source: User said Gita Life operations should have the same features as FOLK.
   - PRD coverage: Sections 2, 4, 8.

9. Existing ICVK admin should not become the new Program operations system.
   - Source: Prior code/context discussion.
   - PRD coverage: Sections 2.2, 7, 8.2.

10. Use two program-specific Next.js applications, one for Gita Life operations and one for FOLK operations, backed by one shared Supabase project/database and two separate Airtable Bases.
   - Source: User requested changing the design from one Next.js app to two apps, with one Supabase database and two Airtable Bases.
   - PRD coverage: Sections 0, 1, 3, 4.1, 4.2, 4.3, 5, 6, 7, 8, 10, 11.
   - Addendum coverage: Recommended App Boundary and Route Shape, Recommended Supabase Auth Mirror, Airtable Integration Notes.

11. Use Program Capability Profiles and configurability guardrails so feature-family parity does not force identical Gita Life and FOLK workflows.
   - Source: Advanced elicitation Cross-Functional War Room; user accepted constraint 1 and constraint 3 only.
   - PRD coverage: Sections 3, 5, 6, 7.

12. Harden the shared-foundation assumptions with explicit Program data isolation and versioned Program Capability Profile review.
   - Source: Advanced elicitation Assumption Audit; user accepted items 3 and 4 only.
   - PRD coverage: Sections 6, 7.

13. Preserve Program-specific workflow emphasis and keep public discovery primary when exposing Portal entry points.
   - Source: Advanced elicitation Inversion Analysis; user accepted failure paths 1 and 4 only.
   - PRD coverage: FR-1, section 7.

14. Exclude daily devotional-discipline tracking from the HKM Program Operations Portals PRD and treat it as future scope.
   - Source: User clarified that this capability is planned for the future and should not be included in this PRD.
   - PRD coverage: Sections 1, 2, 3, 4.4, 4.6, 4.7, 5, 6, 8, 9, 11, 12, and 13 updated to remove current-scope tracking requirements.
   - Addendum coverage: Future Mobile/PWA notes updated to remove current-scope offline queueing for that future capability.
   - Conflict handling: Narrows decision 8 so feature-family parity covers current operations modules only; future daily-discipline capabilities require a separate scope decision or PRD.

15. Use the exact same V1 operational staff roles in Gita Life Ops as current FOLK Ops.
   - Source: User asked whether Gita Life Ops can have the exact same roles as FOLK Ops.
   - Decision: Both Program Apps use `Admin`, `Preacher`, and `Volunteer` as the V1 operational staff Role taxonomy. Gita Life does not introduce separate `Facilitator` or `Super Admin` Roles in MVP.
   - PRD coverage: Sections 1, 2, 3, 4.2, 4.6, 5, 7, 8, 12, and 13.
   - Conflict handling: Resolves deferred decision item 5; member/participant remains a non-staff Program person category, not an operational staff Role.

16. Mirror the currently existing FOLK app user journeys in the PRD.
   - Source: User asked whether the PRD can have the exact same user journeys as the currently existing app.
   - Decision: Replace future-state journey examples with current-app parity journeys: public discovery/registration, session attendance, invited staff sign-in, staff contact capture, session start, live attendance monitoring, admin staff invite/location management, and Airtable management redirect.
   - PRD coverage: Section 2.3 and affected feature journey references in sections 4.1, 4.2, 4.5, 4.6, and 4.7.
   - Conflict handling: Narrows the PRD's journey examples to brownfield FOLK parity while preserving decisions 10 and 11: the proposed product still uses two Program Apps and shared foundations, and Gita Life reuses these journey patterns where modules are enabled.

17. Reconcile Jobs To Be Done, features, MVP scope, metrics, risks, rollout, and deferrals to current-app parity journeys.
   - Source: User asked to change Jobs To Be Done and other sections according to the updated user journeys.
   - Decision: Center the PRD on current FOLK app parity flows: public registration, session-specific attendance, staff auth, staff contact capture, Session creation, live attendance, staff invites/location management, invite auditability, and Airtable management handoff.
   - PRD coverage: Sections 1, 2.1, 2.2, 3, 4.1 through 4.7, 5, 6, 8, 9, 10, 11, 12, and 13.
   - Conflict handling: Authenticated member/participant portal home, announcements, attendance history, seva assignment views, volunteer scanning, advanced preacher care, custom reports/exports, and full sync-health dashboards are explicitly out of MVP parity unless introduced by a later scope decision.
