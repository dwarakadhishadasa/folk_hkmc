- (event) Mode: express. Baseline feat/grid-keyboard-editors-and-theme at 9a43c3b. Hosted in /tmp deliberately: bmad-loop is running and the worktree must stay clean.
- (decision) CORRECTION to the previous spec's claim: the client type ripple is ZERO. lib/supabase/types.ts:154,156,158 already declare these columns as string | null, and Supabase gen-types emits for BOTH text and date. So regenerating that file after the migration produces byte-identical output. The ripple is in validation and migration, not in TypeScript. The earlier 'ripples through the generated Supabase types' claim is withdrawn.
- (decision) VERIFIED low risk: RLS policies reference these columns ZERO times (grep over 20261006010000_scoped_rls_policies.sql = 0 hits). Only created_at/updated_at-style columns are policy-relevant, so the migration touches no policy.
- (constraint) CONFLICT to resolve: lib/manage/api-handlers.ts:90-100 optionalIsoDate validates only the PREFIX /^\d{4}-\d{2}-\d{2}/ and explicitly allows trailing content, because 'contacts already holding a full ISO timestamp still round-trip'. A date column CANNOT hold a timestamp. The migration must therefore TRUNCATE to 10 chars for values with a valid prefix, and the write validation must be tightened in the same change or a valid full ISO timestamp will be rejected by Postgres after deployment.
- (decision) SUPER_DATE_TIME_ZONE is Asia/Kolkata (lib/supabase/data.ts:146) and currentProgramDate() (:269-278) builds YYYY-MM-DD in that zone. Postgres Fri Oct 9 06:55:33 PM IST 2026 is timezone-naitive, so the existing write path is already compatible. The migration must NOT introduce now() AT TIME ZONE conversions, which would shift dates across the day boundary for IST users.

- (capability) CAP-2 last_contacted_on semantics: the column means what its name says. success: the write at insert is either removed or the column is renamed to reflect that it records creation; a contact interaction updates the value; manage-favorites-view.tsx:559 displays the corrected meaning; the audit and the migration both reflect the decision.
- (capability) CAP-3 Schema migration: the three columns are real dates. success: date_of_birth, initial_contact and last_contacted_on are DATE; the cast handles valid prefixes with trailing content by truncating to ten characters; values that cannot be converted are set to NULL only after being reported; the migration is a single reversible file following the repo naming convention; the local stack applies it cleanly.
- (capability) CAP-4 Write validation matches the new type: what the API accepts is what the column can store. success: optionalIsoDate no longer permits trailing content, or the migration truncates it; a value the editor produces round-trips; a full ISO timestamp submitted after deployment is either accepted and truncated or rejected with the handler's own message, never silently dropped by Postgres.
- (capability) CAP-5 Read and chart behavior is unchanged or better: nothing downstream regresses. success: contacts still render in the grid, the dashboard Contact Generation chart still counts them, favorites still shows the value, and every existing e2e row covering edit, filter and sort on a date column still passes.

- (non_goal) No timestamp or timezone conversion. The columns stay calendar dates; date is timezone-naive and the write path already produces program-local YYYY-MM-DD in Asia/Kolkata. Introducing now() AT TIME ZONE would shift dates across the day boundary for IST users.
- (non_goal) No backfill. A contact with no date of birth keeps NULL. Guessing a date is fabrication and the brief forbids it.
- (non_goal) No UI work. The filter modal, the date editor and the grid all live in spec-contacts-premium-grid. This spec makes the storage correct so that spec's operators can rely on it.
- (non_goal) No change to the attendance tables or their rollups, and no retroactive repair of the Airtable migration script's output. The audit reports bad rows; cleaning historical bad data is a separate call.
- (constraint) The audit gates the migration. No ALTER runs until CAP-1's report has been read and the unconvertible rows are known. A cast that throws halfway leaves a partially-migrated table and a column with no working read path.
- (constraint) Single reversible migration file following the repo convention (YYYYMMDDHHMMSS_name.sql; latest is 20261008000000_add_airtable_id_map.sql). The rollback must be provided in the same file as a comment or a paired down migration, because converting a date back to text is lossy for values that were NULL.

- (question) OQ-1 last_contacted_on meaning: it is written once at insert (lib/supabase/data.ts:614-621) and never updated, so it means 'created on', while manage-favorites-view.tsx:559 shows it as 'last contacted on'. Options: (a) update it on every contact interaction so the name becomes true, (b) rename the column to created_on so the name becomes true, (c) leave it and accept the mismatch. Spec assumes (a) - the column is named for the operator's workflow, and 'who do I need to call' is the use. Needs a decision on what counts as an interaction.
- (question) OQ-2 Unconvertible values: rows whose text is not a date at all (e.g. 'unknown', or a numeric string from the Airtable migration). Options: (a) set NULL and report, (b) block the migration until manually repaired, (c) keep the column TEXT and abandon the conversion. Spec assumes (a) only if the count is small and every id is recorded; if the count is large, (b). The audit decides.
- (question) OQ-3 Trailing content: optionalIsoDate deliberately allows a full ISO timestamp after the date prefix because existing rows hold one. A date column cannot. Options: (a) truncate to ten characters in the migration and tighten the validator, losing the time component permanently, (b) keep the column TEXT. Spec assumes (a), since no screen in this app displays a contact timestamp's time.
