- (direction) Decision (user, 2026-10-07): /manage becomes route-per-table (many routes), NOT one page with a table switcher. Supersedes the tabs + ?view= design.
- (direction) Decision (user, 2026-10-07): manage-contacts-table.tsx is REFACTORED ONTO the new grid, not left alongside it. No parallel implementation.
- (capability) CAP-1 virtualized data grid: an operator can work a 200+ row table with smooth scrolling, because row virtualization is mandatory above that threshold.
- (capability) CAP-2 column control: an operator can sort, resize, reorder, show and hide columns on any table.
- (capability) CAP-3 filtering: an operator can narrow a table by free text across all columns and by per-column filters.
- (capability) CAP-4 row selection and bulk actions: an operator can select multiple rows and act on them together.
- (capability) CAP-5 inline editing: an operator can edit a cell in place and have the change persist, with optimistic save and visible failure rollback.
- (capability) CAP-6 per-table routes: an operator can reach any /manage table at its own URL and share or bookmark it; a reload lands on the same table.
- (capability) CAP-7 per-table data loading: opening a table loads only that table's rows, so a large contacts table does not delay the sessions or attendance views.
- (capability) CAP-8 keyboard operation: an operator can drive the grid and the portal from the keyboard, including a command palette for jumping between tables.
- (capability) CAP-9 explicit states: every table renders distinct loading, empty, and error states rather than a blank surface.
- (capability) CAP-10 scope preservation across routes: an operator's admin/preacher scope survives navigation between table routes.
- (constraint) Stack is fixed: Next.js 16 App Router, React 19, Tailwind v4, shadcn/ui new-york, Supabase. No substitutions, because components.json and the two deployed apps (apps/folk, apps/gita-life) already pin these.
- (constraint) Grid model must come from @tanstack/react-table v8 and row virtualization from @tanstack/react-virtual. Hand-rolled sorting/filtering state is banned: the current manage-contacts-table.tsx sorts via useMemo and breaks at scale, which is the defect being fixed.
- (constraint) All data access flows through the existing lib/supabase/manage.ts and lib/manage/api-handlers.ts modules. Components must never call Supabase directly. Scripts/verify-monorepo-guardrails.mjs enforces a server-only boundary that client components may not cross.
- (constraint) RLS remains the sole authorization enforcement point. The client may render a disabled affordance for non-editable fields but must not re-implement authorization logic, or the boundary in verify-monorepo-guardrails.mjs and the RLS policy matrix both become wrong.
- (constraint) manage-contacts-table.tsx is refactored onto the new grid and its hand-rolled sort/filter removed. A parallel second table implementation is explicitly forbidden; two grids means two sets of bugs and a permanent migration tax.
- (constraint) The dashboard overview stays a distinct non-table view, and /manage redirects to it. The rest of the views (contacts, sessions, attendance, favorites) each get their own route.
- (constraint) Route changes mean the old ?view= query param and history.replaceState tab sync disappear. A /manage?view=<x> request must redirect to the matching /manage/<x> route so existing bookmarks and links do not 404.
- (constraint) The admin/preacher scope toggle remains a real server-affecting navigation carried as ?mode= on every table route, because it changes what the server reads, not just what is displayed.
- (constraint) Delivered incrementally: the grid plus the contacts refactor lands first, then work pauses for human review before a second table is built on the pattern. Unreviewed replication across four tables is the failure mode being avoided.
- (non-goal) Airtable parity beyond the capabilities listed here: linked-record cells, formula fields, grouped/collapsed rows, a relational data model, and undo/redo history are out of scope. Staff use this to manage contacts, not to model a database.
- (non-goal) No real-time collaborative editing, presence, or multi-user conflict resolution. Single-operator tool.
- (non-goal) No offline editing, background sync queue, or local persistence of grid edits. There is a lib/offline-sync.ts in the repo, but wiring it to the grid is a separate concern.
- (non-goal) No change to the Supabase schema, RLS policies, or the existing API route surface. This work is presentation and navigation only; data-layer changes are separate stories.
- (assumption) Assumed @tanstack/react-table v8 and @tanstack/react-virtual are React 19 compatible. NOT verified at authoring time; if the peer range excludes React 19, that becomes a blocking decision for downstream skills.
- (assumption) Assumed real contact volume exceeds a few hundred rows, which is what makes virtualization and TanStack Table necessary over the current useMemo approach. Exact production row counts were not provided.
- (assumption) Assumed both apps/folk and apps/gita-life expose /manage and must keep working after the route change. Their manage/page.tsx files are byte-identical today (56 lines each).
- (assumption) Assumed the dashboard overview can render from a narrower payload once each table loads its own data. If ManageDashboard genuinely needs every table's rows, CAP-7 conflicts with it and the dashboard must keep an aggregate query.
- (question) Does anything outside /manage link to or bookmark a ?view= URL? A repo-wide grep found only manage-portal.tsx:23 constructing it, so a redirect may be sufficient, but external bookmarks in staff browsers cannot be enumerated from the repo.
- (question) Should ManageDashboard keep receiving the full ManagePortalPayload? If the dashboard charts need rows from every table, per-table loading (CAP-7) does not apply to /manage itself and the dashboard keeps its own aggregate load.
- (question) Is server-side pagination in scope, or is client-side virtualization over the full scoped row set acceptable? This decides whether CAP-7 means one query per table or a paginated query, and materially changes the data-access work.
- (question) Should bulk actions (CAP-4) ship in the first slice or wait for the contacts pattern to be reviewed? Bulk edit implies a new write endpoint or batch semantics in lib/manage/api-handlers.ts.
- (decision) All five open questions CLOSED (user, 2026-10-07): 1-3 resolved to best industry standard, 4 keeps the human review gate, 5 confirmed intentional. Full reasoning in the new companion data-loading-decision.md.
- (decision) ?view= question closed: nothing outside /manage produces such a link; only manage-portal.tsx:23 does. The unenumerable-bookmark worry inverts — an origin-agnostic redirect absorbs every bookmark without needing to enumerate it. Implement as a permanent 308 via permanentRedirect(), firing before any data load.
- (constraint) The ?view= redirect MUST preserve ?mode=. /manage?view=contacts&mode=preacher must land on /manage/contacts?mode=preacher. Dropping the query silently promotes a Preacher following a shared bookmark into admin scope — the exact CAP-10 failure, arriving through the one path nobody tests. An unrecognized or absent view falls back to /manage.
- (decision) ManageDashboard does NOT need ManagePortalPayload (verified against manage-dashboard.tsx:252-272). Rows are touched in exactly three places, all reductions to a count: contacts.length (line 270), sessions.length (line 271), and a sum of session.attendees.length (line 265). Everything else renders from the pre-derived charts object.
- (decision) Dashboard payload is now a summary shape: { scope, generatedAt, charts, totals: { contacts, sessions, attendanceRecords } }. CAP-7 binds the four table routes; /manage is an aggregate view, explicitly exempt. Recorded as a constraint in SPEC.md.
- (note) Honest limit of the dashboard split: the server still reads every contact/session/attendance row to build the chart series (manage.ts:694-706). Nothing makes the dashboard query cheap, and aggregating in Postgres is barred by the no-schema-change non-goal. What changes is the wire: O(rows) becomes O(series). If it ever bottlenecks, the fix is a Postgres view or RPC — a separate story.
- (decision) Pagination closed: client-side virtualization over the full scoped row set, TanStack client row models with manual* flags false. Rationale: collectPagedRows (manage.ts:200-218) already materializes the full scoped set so server-side paging is new work, not removed work; CAP-3's cross-column free-text search has no indexed server equivalent without a schema change; CAP-2/CAP-4/CAP-5 all get harder under paged rows.
- (note) Virtualization bounds the DOM, not the transfer. A 5k-row table can scroll smoothly while shipping megabytes of RSC payload. The two costs are independent: virtualization handles render cost (CAP-1), per-table loading plus the aggregate-only dashboard handle transfer cost (CAP-7). A plan doing only the first is still slow to first paint.
- (constraint) Grid state (sort, filters, column order, visibility, size) lives in the URL, not component state. This makes CAP-2/CAP-3 persistence free and keeps a future server-side pivot a data-source swap behind the manualPagination/manualSorting/manualFiltering flags instead of a rewrite. Holding it in component state "for now" is the decision that would make that migration expensive.
- (constraint) Pagination migration trigger, any one measured per table (not portal-wide): >10k scoped rows, >1MB gzipped payload, >100ms sort/filter keystroke latency, or >2s server time for one table route. Then move that table to server-side row models with Supabase .range() paging at 200/page.
- (decision) Bulk actions (CAP-4) ship in slice one. Row selection is a grid primitive all four tables need, so deferring it means building the grid twice; the bulk ACTION is the part that reaches lib/manage/api-handlers.ts and is what the human review gate validates before three more tables copy it.
- (decision) resolveManageMode's fail-open coercion of non-"preacher" to "admin" is INTENTIONAL and stays (user, 2026-10-07). It is safe because RLS is the enforcement point and app-layer narrowing can only shrink the set (manage.ts:520) — a malformed mode cannot expose rows outside the caller's RLS scope. Residual risk is a Preacher seeing more of their own scoped rows than the preacher filter would show: a UX surprise, not a leak.
