- (finding) PRE-MORTEM: the spec argued every decision as a RISK REDUCTION against the source app and none as introducing risk. The blind spot is adoption — CAP-1 tests capability ("a volunteer lands on a working list"), never adoption. In the source an "enabler" was a small committed set; here Volunteer is a broad public.users.role. Assignment succeeding means nothing is blocked, so nothing surfaces for three weeks.
- (finding) PRE-MORTEM: the rail's entire intuition value depends on a short queue and the spec never bounds it. Realistic queues are 300-500; a rendered list janks on every advance, mid-conversation.
- (finding) PRE-MORTEM: CI does not run e2e (repo testing policy), so the one test protecting the volunteer scope boundary runs only when someone remembers — typically right after lib/authz.ts or proxy.ts changed.
- (finding) ASSUMPTIONS: the "laptop browser" assumption was contradicted by the user's own calling loop, which describes the native phone app. A self-inflicted inconsistency, not a user error.
- (finding) ASSUMPTION: record_call_disposition does not need SECURITY DEFINER. Nothing calls it as authenticated — writes go through route handlers on the service-role client, which bypasses RLS anyway. A service-role-only function needs grants, not SECURITY DEFINER; the spec over-built a privilege boundary that adds attack surface without safety.
- (finding) ASSUMPTION: upsertStaffUser calls auth.admin.listUsers({page:1, perPage:200}) — a bounded scan of the first 200 auth users. Past that, a returning person's email is not found and createUser makes a SECOND auth identity for them.
- (finding) BOUNDARY: dialer_assignments.campaign_id and dialer_survey_responses.question_id are both on delete cascade, so deleting a campaign destroys a live queue and removing a survey question destroys historical answers — silently, with no confirm.
- (finding) BOUNDARY: two tabs on one queue write two call_logs rows for the same assignment; the unique constraint is per-call-log so nothing is violated and every campaign number doubles.
- (finding) BOUNDARY: is_active=false hides a caller from pickers but does not stop them writing call_log rows indefinitely — deactivation with no teeth.
- (finding) BOUNDARY: "queue empty because finished" and "queue empty because no work" are one screen with opposite meanings, conflated in the source and unaddressed here.
- (finding) SECOND-ORDER: the leaderboard rewards volume, and under click-to-call volume is the ONE thing the system cannot verify — every outcome is self-reported. CAP-8 measured exactly the unmeasurable.
- (finding) SECOND-ORDER: dropping caller_id from the assignment unique key makes assignment a move, so there is NO record of who was assigned when. That history now lives only in call_logs.caller_id. Unstated, it is the exact ambiguity that broke the source app.
- (finding) ANALOGY: trial-calling and call-centre domains both define a re-contact policy (N attempts then close out). This spec had none, so unreachable contacts were permanent queue debt.
- (finding) ANALOGY: a call centre's primary operational number is "assigned but never attempted" — the supervisor's cue to nudge someone. Absent from the funnel, and its absence is why the adoption failure is invisible.
- (finding) ANALOGY: wrap-up time and inter-call pacing are different things. Conflating them makes a caller who records carefully look slow.
