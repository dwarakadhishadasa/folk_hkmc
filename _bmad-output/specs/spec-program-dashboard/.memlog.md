- (direction) User asked for a spec for a stellar dashboard covering contacts collected in the field, campaign calls, session invitations and attendance, useful to preachers and to admins who report upward.
- (direction) Route is top-level /dashboard in both apps; the live-attendance surface already moved to /sessions/[id]/live on dev, so /dashboard is the overview page.
- (direction) Reuse the All preachers / Own scope switch pattern from Manage -> Dashboard, carried in ?mode= and narrowing every section.
- (direction) Invite is measured from a reached call: if a contact is reached, they are considered invited. A campaign links to the session it invites people to.
- (direction) Admin sharing is on-screen only in v1; no export, PDF, print or email.
- (direction) Period control offers presets plus custom month and year selection, and lives in the URL so a shared link keeps its view.
- (decision) The dashboard roles are Admin, Preacher and Assistant; a Volunteer has no dashboard and keeps landing on /contact.
- (decision) Assistant scope resolves through assignedPreacherUserId; a missing, inactive or non-Preacher assignment is an empty scope with an explanation, never a refusal or a widening.
- (decision) Campaign gains a nullable session_id FK to sessions, chosen by a Session dropdown on the campaign create and edit forms; the link is same-program and ON DELETE SET NULL.
- (assumption) The Session dropdown lives on the campaign form, not on the attendance screen; the data link is the same either way.
- (decision) Aggregation lives in two SECURITY INVOKER PostgreSQL functions callable through .rpc(): dashboard_overview for the page payload and dashboard_candidates for the drill-down list; both service_role-only.
- (constraint) One definition per number: the RPC computes it once, the server loader parses it, and no component recounts or re-derives a figure.
- (decision) The hero pipeline follows the period cohort of contacts collected in the window: collected, assigned, called, reached (invited), confirmed, attended their linked session; organic attendance is reported separately.
- (decision) The KPI band carries five tiles: contacts collected, calls made, contacts reached, contacts confirmed, people attended.
- (decision) Attendance health covers sessions held, unique attendees, check-ins, new versus returning attendees, repeat rate and a 12-month attendance trend.
- (decision) Focus segments are confirmed-not-attended, ready-to-invite, committed-not-invited, new-untouched and fading regulars; they are deterministic, overlapping and each carries a reason and contact details.
- (decision) The team table compares preachers in All scope and locations in Own scope, with contacts, calls, reached, confirmed, sessions, attendees and last activity.
- (decision) A data-coverage card reports contacts missing a location, an assigned preacher, a first-contact date or a collector.
- (decision) The live band is retained: live sessions in scope with check-in counts, refreshed every 20 seconds while the tab is visible, linking to /sessions/[id]/live.
- (decision) The campaign section lists active campaigns with their linked session and funnel, and flags an active campaign with no linked session rather than showing a silent zero.
- (constraint) Scope predicates match campaign_progress and loadManagePortalData: contacts by assigned_preacher_id, sessions by preacher_id or created_by, attendance by session, call logs by the assignment contact's assigned_preacher_id.
- (constraint) Attendance belongs to the session's scope; attendees are not intersected with the scoped contact set, so a visitor from another preacher's patch still counts.
- (constraint) Every figure is program-scoped; no query, function or link crosses programs.
- (constraint) Dates use the Asia/Kolkata programme day and inclusive boundaries; no wall-clock UTC date arithmetic on the server.
- (constraint) No number on the dashboard may disagree with the surface that owns it for the same scope and period.
- (constraint) Performance budget: dashboard_overview p95 under 500 ms at 5k contacts and 50k call logs; server render under 1.5 s; the page issues one overview RPC plus one candidates RPC, not one per campaign.
- (constraint) Core reads failing is a 500; the optional campaign module fails in isolation and renders a section error, so contacts, attendance and focus still render.
- (constraint) Reuse the existing design system and components; no new visual language, no hex codes in the page, mobile-first at 360 px.
- (constraint) modules.dialer false removes every campaign and call section and skips the dialer RPC entirely.
- (constraint) The legacy /manage Dashboard charts stay for v1; the new page does not restate the status-quo chart or any metric under a second definition.
- (non_goal) No export, PDF, print, email or scheduled report in v1.
- (non_goal) No predictive scoring, ML ranking or opaque recommendation; focus rules are deterministic SQL a reader can inspect.
- (non_goal) No Volunteer dashboard, no bulk actions and no inline editing from the dashboard.
- (non_goal) No new attendance capture flow and no historical backfill of campaign-session links.
- (non_goal) No cross-program rollup.
- (assumption) CONFIRMED means the latest reached call log has status_group CONFIRMED, matching campaign_progress; MAY_COME is not confirmed.
- (assumption) This quarter and this year are calendar periods in the programme timezone.
- (assumption) This worktree is cut from an older dev; dev already holds the sessions live routes and the contacts section, so implementation starts from a rebase.
- (question) Should the legacy /manage Dashboard tab be retired or redirected once /dashboard ships?
- (question) Are the focus thresholds right for FOLK: 7 days untouched, 60 days fading, 3 lifetime attendances for the committed core?
- (question) Should an upcoming confirmed invitee appear in Confirmed, not attended before the session, or only after it?
- (event) Create run started from the user's dashboard direction, the WDS dashboard page, the autodialer contract and the live schema.
- (decision) The five pipeline bars are strictly nested (collected, assigned, called, reached, confirmed); attendance is a readout below the bars with a confirmed/unconfirmed split, because arriving without confirming is possible.
- (decision) The campaign card is campaign-lifetime, not period-scoped, and must equal campaign_progress for the same campaign and scope; every other section follows the selected period or says it does not.
- (note) dashboard_overview carries the header scope counts and the reach, confirmation, repeat and average rates, so no component derives a figure; p_has_dialer gates every dialer CTE.
- (note) The performance budget is one overview RPC per dashboard load and one candidates RPC per candidate page; campaign figures come from the overview, never one RPC per campaign.
